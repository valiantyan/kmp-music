# 17 个本地音频发现 issue 对抗式审查纪要

## 审查结论

这 17 个 issue 的主线方向正确：先用红灯测试固定 positive-only 安全语义，再实现显式完成覆盖模型，最后分别收敛 Android、Desktop、iOS、取消/失败状态和文案展示。

对抗式审查发现原 issue 集有 5 个容易翻车的点，已直接补进对应 issue：

- `01/03` 原本没有强约束主边界，后续 agent 可能修到共享内存合并而漏掉持久化仓库；现在明确主边界是 `PersistentMusicLibraryRepository.applyScanResult`。
- `02/04/05` 原本仍可能让仓库从 `request`、`discovered` 或 `sourceSummaries` 猜测删除权；现在要求完成覆盖必须显式表达。
- `06/07/08` 原本没有说清旧数据缺少具体来源身份时怎么处理；现在要求缺少具体来源身份的旧记录不能自动获得删除权。
- `11/12` 原本只覆盖取消后的状态，没有覆盖 PRD 的“单任务扫描”和“扫描中入口变取消扫描”；现在并入最小测试和实现要求，保持 17 个 issue 不变。
- `15/16` 原本使用“扫描页”表述，但当前源码不一定存在独立扫描页；现在收敛为本地音乐入口、首页扫描入口、来源页或其展示模型，避免为了文案新建多余页面，并补上扫描完成后不自动跳离当前页面。

## 最可能翻车点

- 只看歌曲数量而不看具体歌曲 id。后续测试必须证明文件夹 A 的具体歌曲仍可用、Android 缺失的具体歌曲会下线、iOS 旧导入的具体歌曲不会被替换。
- 把来源摘要当成删除授权。来源摘要可以用于展示，但不能证明整个 `sourceKind` 已完整扫描。
- 把 iOS 导入理解成复制到沙盒永久保活。PRD 的语义是来源可访问性和平台可恢复来源引用，不是脱离原始授权来源。
- 把用户取消当作普通失败，或把失败当作取消。两者都不能删除未处理旧歌，但 UI 文案必须区分“已取消”和“扫描失败”。
- 扫描或导入完成后自动导航离开当前页面。PRD 要求用户能留在当前页面检查结果。
- partial scan 误伤收藏或播放队列。保留旧歌时也要保留它的用户状态，不应因为没有完整来源证据就从恢复队列里消失。
- 为了平台文案修改高保真原型。生产行为应改真实 KMP App 的共享状态、组件或平台适配。

## 已修改的 issue

- `01`：补主测试边界和具体歌曲 id 断言。
- `02`：补显式覆盖契约和三类覆盖语义。
- `03`：补持久化合并主边界和禁止从发现结果推导删除权。
- `04/05`：补 Android 完整覆盖必须由成功扫描结果显式声明。
- `06/07/08`：补 Desktop 具体目录身份、旧数据安全和双向断言。
- `09/10`：补 iOS 累加模型、非沙盒保活假设和平台来源引用边界。
- `11/12`：补单任务扫描、扫描中取消入口和无确认取消。
- `13/14`：补失败路径必须保留旧歌，并与取消文案区分。
- `15/16`：补当前源码没有独立扫描页时的落点，以及扫描完成不自动跳离当前页面。
- `17`：补最终审查必须回看 PRD 原始验收、具体歌曲 id、取消入口、收藏/队列和页面停留。

## 后续执行建议

按原编号继续推进。每个实现 session 仍只拿一个 issue；遇到 `11/12` 时要特别注意它们现在覆盖“取消状态 + 单任务扫描入口”的 PRD 缺口，如果实现范围变大，应优先保持测试最小化，而不是扩成完整后台扫描系统。
