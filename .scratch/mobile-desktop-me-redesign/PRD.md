# 我的页 Figma 重设计与最近播放页 PRD

## 问题陈述

用户希望生产版 KMP Music 的“我的”页从当前偏登录、收藏摘要和常听歌手的旧结构，更新为 Figma 节点 `919:439` 所表达的个人中心结构。移动端需要严格还原 Figma 的内容区视觉；Desktop/macOS 端也需要同步采用新的信息结构，但保持桌面端自己的宽屏布局语义。

当前“我的”页没有使用真实最近播放列表，也没有完整的“最近播放页”。用户需要在“我的”页看到最近播放摘要，点击“查看全部”后浏览完整最近播放歌曲列表，并且从摘要或完整列表播放任意歌曲时，都沿用完整最近播放歌曲列表作为播放队列。

## 解决方案

移动端“我的”页按 Figma 节点 `919:439` 的内容区重做：页面从头像资料区开始，不再显示页面内“我的”标题栏；展示固定头像、编辑浮层、三项统计、扫描音乐、最近播放摘要和三行设置菜单。底部 Tab 和全局迷你播放器继续由现有全局 chrome 负责，本需求不修改它们。

Desktop/macOS 端“我的”页同步调整为同一信息结构：个人资料头、统计、扫描音乐、最近播放、设置菜单，但布局按桌面 workspace 适配，不把 390px 手机稿等比例拉伸。

新增“最近播放页”二级页面。手机端和 Desktop/macOS 端使用同一产品语义：展示完整最近播放歌曲列表，支持点击播放、当前播放高亮和单曲更多菜单。移动端从“我的”页“查看全部”进入普通二级页面；Desktop/macOS 端在 workspace 中渲染完整列表页。

最近播放歌曲列表只展示当前仍能解析到歌曲实体、且可播放的历史歌曲。历史中已经从本地曲库移除、无法解析或不可播放的歌曲不显示，也不能进入最近播放队列。

## 实现决策

- 使用 Figma 设计节点 `919:439` 作为移动端“我的”页内容区视觉来源。
- 移动端严格还原 Figma 的内容结构、间距、头像区、统计区、快速功能、最近播放和设置菜单。
- 移动端“我的”页去掉页面内标题栏，内容从头像资料区开始。
- 底部 Tab 和全局迷你播放器不属于本需求实现范围，继续由现有全局 chrome 管理。
- Desktop/macOS 端纳入本轮范围，但只做桌面适配版，不把 390px 手机稿等比例拉伸。
- Desktop/macOS 端采用与移动端一致的信息结构：个人资料头、统计、扫描音乐、最近播放和设置菜单。
- 头像必须使用从 Figma 节点导出的静态位图作为生产 App 资源。若当前仓库尚无独立头像资源，实现前应先从 Figma 导出并加入 `composeResources/drawable`，不得用随机专辑封面或运行时账号头像替代。
- 头像编辑图标只做静态视觉，不绑定点击、权限、相册或登录。
- 用户名固定为“高保真听众”，副标题固定为“音乐是我的灵魂”。
- 本轮“我的”页内容区不展示旧登录卡片或“立即登录”按钮；现有登录页面、登录路由和未来云同步占位能力不在本需求中删除或重构。
- 统计区歌曲数使用真实曲库歌曲数。
- 统计区歌单数固定展示 12，不创建歌单领域模型、数据源或页面。
- 统计区听歌时长固定展示 365，不创建听歌时长统计模型、数据源或页面。
- “扫描音乐”在移动端打开现有扫描音乐二级页面，由扫描页承载扫描设置和扫描动作。
- “扫描音乐”在 Desktop/macOS 端复用现有桌面扫描动作或添加文件夹入口，不打开 `AudioScan` 空占位页，也不新增另一套桌面扫描 UI。
- 使用“最近播放歌曲列表”表示由真实播放历史生成、按最近播放倒序排列的歌曲集合。
- 最近播放歌曲列表只包含当前曲库可解析且可播放的歌曲；不可解析、已移除或不可播放的历史项应被过滤，不显示在摘要、完整页或播放队列中。
- 新增“最近播放页”二级页面，作为完整最近播放歌曲列表的浏览入口。
- “最近播放页”不是播放日志管理页，不负责清空、编辑或审计历史。
- 移动端“我的”页最近播放摘要只显示 `最近播放歌曲列表` 的前 3 条。
- 点击移动端摘要中的任意歌曲时，播放队列使用完整最近播放歌曲列表，播放起点是被点击歌曲。
- 点击最近播放页中的任意歌曲时，播放队列同样使用完整最近播放歌曲列表。
- 最近播放行右侧三点按钮接入现有单曲更多菜单。
- “查看全部”文案后添加右箭头图标，点击进入最近播放页。
- 最近播放摘要、最近播放页和 Desktop/macOS 最近播放列表都必须接收当前播放歌曲信息，并在当前播放歌曲行使用红色标题高亮。
- 最近播放摘要、最近播放页和 Desktop/macOS 最近播放列表都应保留现有播放中辅助标识。
- 最近播放为空时，不留空白；摘要和完整页都显示轻量空态文案。
- “存储管理”“主题与外观”“关于”三行在移动端和 Desktop/macOS 端都只显示 UI，不绑定点击。
- 复用现有 controller、导航、播放和单曲更多菜单能力。新增边界应控制在最近播放页路由语义和最近播放行或列表 UI 组件。
- 不新增 repository、持久化表、后端接口、账号体系、歌单能力或听歌时长统计能力。
- 不修改高保真原型目录来实现生产 App 行为。

## 测试决策

- 好测试应断言用户可感知行为，不应断言私有 Composable 拆分、局部变量或具体绘制实现。
- 最高测试边界是 App 路由与页面行为边界。测试应覆盖从“我的”进入最近播放页、返回行为和普通二级页语义。
- 播放行为测试应断言从最近播放摘要点击歌曲时，传入播放的队列是完整最近播放歌曲列表，而不是可见的 3 条摘要。
- 播放行为测试应断言最近播放页点击歌曲时，同样使用完整最近播放歌曲列表作为队列。
- UI 行为测试应覆盖当前播放歌曲高亮规则，至少证明最近播放列表会根据当前播放歌曲标识渲染高亮状态。
- 单曲更多菜单行为应通过现有 more 面板入口验证，不新增重复面板测试。
- 最近播放空态应作为外部行为测试：没有最近播放歌曲时页面显示空态文案，而不是崩溃或留白。
- 移动端导航测试应复用现有根页面、二级页面和 chrome 策略测试先例。
- 新增最近播放页路由后，导航模型测试应覆盖路由名、返回栈和普通二级页分类。
- Desktop/macOS 端如果已有桌面路由测试，应覆盖 Desktop/macOS “我的”进入最近播放页的路由行为；如果没有现成 seam，则以共享导航模型和可复用列表行为测试为主。
- 最近播放数据测试应覆盖历史中包含不可解析、已移除或不可播放歌曲时，摘要、完整页和播放队列都只使用可解析可播放歌曲。
- 视觉验证应对照 Figma 节点 `919:439`，重点检查移动端头像区、统计区、快速功能、最近播放 3 条和设置菜单。
- 实现后至少运行 Android Kotlin 编译。因为涉及共享导航和 controller 行为，也应运行覆盖共享逻辑的测试命令。

## 对抗式审查

- 最可能翻车的一点是把歌单和听歌时长误做成真实领域能力。它们本次只能是静态统计展示。
- 第二个风险是“我的”页摘要只传 3 条歌曲给播放队列，导致下一首只能在 3 条内循环。摘要播放必须使用完整最近播放歌曲列表。
- 第三个风险是为了 Figma 静态视觉丢掉当前播放红色高亮。最近播放列表必须保留全局播放反馈。
- 第四个风险是 Desktop/macOS 端打开空的扫描占位页。桌面扫描音乐应进入现有添加文件夹或扫描入口。
- 第五个风险是给设置菜单三行接上旧设置、关于或来源管理，造成两端行为和本 PRD 不一致。本轮只显示 UI。
- 第六个风险是实现时拿现有专辑封面冒充 Figma 头像。头像必须来自 Figma 导出的静态位图资源。
- 第七个风险是把播放历史里的陈旧 songId 直接渲染出来。最近播放歌曲列表必须先过滤当前不可解析、已移除或不可播放的歌曲。
