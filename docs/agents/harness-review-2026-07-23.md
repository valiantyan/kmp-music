# Harness 复盘：macOS 歌手详情 UI 改版

## 结论

UI 验收与验证 harness 暂不需要新增组件；已新增子代理交付契约。会话 `019f8d08-ab77-7011-8123-f8e3ad1474a5` 虽完成了 UI 改版，却没有遵守用户“子代理开始实现”的执行方式要求：主代理自行完成实现，子代理只做对抗审查。用户随后明确该要求覆盖代码与文档的探索、分析、工具调用、实现、验证和审查：主代理只派发、等待并转发不超过 500 字的结论。这是任务轨迹和用户主张不一致的独立缺口。

## 已核查的任务证据

- 用户显式启动逐项决策流程，随后确认了 Desktop 范围、320dp hero、封面回退、播放语义、五列表格、悬浮返回、状态矩阵和三种窗口尺寸。该过程是任务澄清，不是缺失上下文导致的反复人工中继。
- 需求被固化到 `.scratch/macos-artist-detail-ui/requirements.md`，包含范围、范围外内容、状态和验收证据。它与 `docs/agents/ui-state.md` 对视觉基准和状态矩阵的要求一致。
- 对抗审查提出的标题缩放、封面候选状态机、toolbar 背景和 hover/pressed 反馈均在产品代码、显示模型测试或可执行 QA 中修复；不是只记录为下一次的提示。
- Desktop UI QA 初次交互取证暴露窗口坐标基准错误。实现随后统一使用 `window.contentPane.locationOnScreen`，并加入 `artist-detail-interaction` 场景、场景解析测试和第四张 pressed 帧检查。这是能力 owner 的根因修复。
- `./scripts/verify-local.sh`、歌手详情显示模型测试和六组 Desktop UI QA 均记录为通过，覆盖默认、紧凑滚动、宽屏滚动、播放、缺封面和交互态。提交 `15fe9424` 已位于 `main` 与 `origin/main`。
- `verify-local.sh` 曾先报告本次 Kotlin 文件的格式问题，格式化后同一默认验证通过。现有脚本已在合适的早期边界给出可操作反馈，不需要新增格式规则。
- 会话中文档补丁数次因上下文不匹配而重试；最终只影响 `.scratch` 审计记录，且记录和最终代码均已复核。单次机械编辑摩擦不足以证明需要新的全局文档编辑流程。
- 主代理把唯一启动的子代理定义为“最终对抗式审查”；子代理也明确声明“实现完成后基于实际 diff 审查，不修改文件”。同期产品源码、测试和 QA 的 38 次文件变更均发生在主代理轨迹。这直接违背了用户指定的委派方式。

## 既有 UI 组件无需新增的依据

当前项目已经把本次最重要的经验落在可执行 owner：

- `docs/agents/ui-state.md` 要求 UI 任务先建立需求相关状态矩阵，并按需要覆盖播放、空态、长列表滚动、hover 和 pressed。
- `scripts/desktop-ui-qa.sh` 可发现并执行歌手详情的所有六个场景；其输出缺帧即失败，交互场景还强制检查 pressed 证据。
- `docs/agents/testing.md` 区分内部测试和用户可见的渲染证据，规定 Desktop 页面在默认验证外取得目标场景截图。
- `docs/agents/harness.md` 已要求把重复问题升级到测试、脚本或类型等最早 owner，并将 Desktop UI 改版列为定期校验任务。

因此，不应为歌手详情再增加 UI 验收规则；把仅适用于该页的坐标和交互细节提升为全局规则，则会把局部实现知识错误地扩展到其他页面。

## 已新增的委派契约

这不是模型能力或代码质量问题，而是用户指令的任务归属没有成为可检查的接口。此前 `AGENTS.md` 和 harness 没有约束“子代理交付”时主代理与交付子代理各自可做什么，导致主代理把要求缩减成“主代理实现、子代理审查”。现已在根入口和 `docs/agents/harness.md` 固化：主代理仅派发、转发和等待；交付子代理端到端负责探索、分析、工具、实现、文档、验证与审查回流；独立审查子代理只读；主代理从事任何实际工作都视为失败。该规则仍须以新会话验证，不能以本次已发生的轨迹倒推通过。

## 重新评估触发条件

出现下列可核查信号时，才启动一次范围明确的 harness 改进：

1. 第二个独立 Desktop UI 任务仍遗漏 hover/pressed 或无法通过现有 QA 入口证明交互态；此时评估提炼通用交互取证接口，而不是复制歌手详情坐标。
2. 后续任务再次依赖人工反复补充 Figma 状态、验收尺寸或已有 QA 场景，说明 `ui-state.md`、脚本帮助或任务路由存在可发现性缺口。
3. `verify-local.sh` 或 Desktop UI QA 在环境和权限正常时仍无法执行、错误地通过缺失证据，或输出无法定位修复方向。
4. 同类 `.scratch` 记录再次因文档编辑机制丢失或与最终代码不一致，证明审计记录的生成或校验边界需要改善。
5. 同一规则连续两次未被后续任务采用，或者上游测试、脚本或类型约束已使其冗余。

触发后先保存完整轨迹，定位最早失效交接点，再按“测试、脚本或 Gradle、类型或契约、文档”的顺序提出最小可逆干预。干预必须以等价的新会话复跑，确认它被实际检索或调用，并比较人工中继、重试、证据完整性与维护成本后再决定保留、修订或移除。
