# GitHub 提 BUG 使用指南

本文面向在 GitHub 上提交 BUG 的用户。提交前请尽量把问题写到“别人可以照着复现”的程度；信息越完整，修复越快，也越不容易修错方向。

## 提交入口

1. 打开项目 GitHub 仓库。
2. 进入 `Issues` 页面。
3. 点击 `New issue`。
4. 选择一个 BUG 入口：
   - `BUG 报告`：表单版，适合逐项填写。
   - `BUG 报告（Markdown 模板）`：正文会自动填入一整段模板，适合直接按 Markdown 修改。

两个入口都可以使用，后续修复流程相同。

## 必填内容

提交 BUG 时，请至少填写这些内容：

- 问题现象：你遇到了什么问题，影响哪个页面、功能或流程。
- 复现步骤：从打开应用开始，一步一步写出如何触发问题。
- 期望行为：正常情况下应该发生什么。
- 实际行为：现在实际发生了什么。
- 验收标准：修复后如何确认问题已经解决。

## 可选内容

这些信息不是必填，但强烈建议提供：

- 设备/平台：Android、iOS、Desktop/macOS、共享逻辑或其他环境。
- 版本或提交：应用版本、分支名、commit hash、APK 版本等。
- 截图、录屏或日志：页面截图、操作录屏、崩溃日志、控制台日志、bugreport 等。

如果不确定平台或没有日志，可以留空，不要为了凑内容写猜测。

## 推荐写法

### 问题现象

写清楚用户能看到的异常，不要只写“坏了”“有问题”。

推荐：

```text
在 Android 首页点击迷你播放器后，没有进入播放页，仍停留在首页。
```

不推荐：

```text
播放页有问题。
```

### 复现步骤

复现步骤要能让维护者照着走。请使用编号列表。

推荐：

```text
1. 打开应用
2. 在首页点击任意歌曲开始播放
3. 点击底部迷你播放器
4. 观察是否进入播放页
```

不推荐：

```text
点几下播放器就出问题。
```

### 期望行为

描述正确结果。

```text
点击迷你播放器后，应打开当前歌曲的播放页。
```

### 实际行为

描述错误结果，并尽量写明是否稳定复现。

```text
点击后仍停留在首页，没有任何跳转。重复 3 次都能复现。
```

### 验收标准

验收标准要可验证，建议写成勾选项。

```markdown
- [ ] 按上述步骤点击迷你播放器后能进入播放页
- [ ] 播放页显示当前播放歌曲
- [ ] 首页底部迷你播放器状态仍保持正确
```


## 提交后会发生什么

提交后，维护者或 Codex 会先确认信息是否足够：

- 信息足够：Issue 会进入修复流程。
- 信息不足：Issue 会被标记为 `needs-info`，并在评论中说明需要补充什么。
- 不属于 BUG：维护者会说明原因，可能转为讨论、需求或关闭。

进入修复流程后，Codex 会把 GitHub Issue 镜像成本地 issue，完成修复、测试、提交、push 后，再把修复日志写回 GitHub Issue。
